# teraflow v0.6.0 他言語対応（i18n）設計書

> cmd_196 — teraflow の CLI メッセージ・AI プロンプト・テンプレートを多言語対応する設計


## 1. 現状分析

### 1.1 CLI メッセージの現状

teraflow の CLI メッセージは全て Go ソースコード内にハードコードされている。

| 箇所 | 言語 | 例 |
|------|------|-----|
| cobra `Short`/`Long` | 英語 | `"Validate CoDD consistency"` |
| `fmt.Fprintf` 出力 | 英語 | `"Valid: %t\n"`, `"Scan complete: %d/%d"` |
| `fmt.Errorf` エラー | 英語 | `"--phase is required"` |
| エラーコード（TF-CCNN） | 英語 | カタログ管理済み |

cmd/ 配下のファイル数: 約 40 ファイル、メッセージ文字列: 推定 300〜400 箇所。

### 1.2 AI プロンプトの現状

| ファイル | 言語 | 内容 |
|---------|------|------|
| `skills/discovery.yml` | 日本語 | system/init/confirm プロンプト |
| `skills/req.yml` | 日本語（一部英語） | requirements スキル |
| `skills/design.yml` | 英語 | design-discussion スキル |
| `skills/review.yml` | 英語 | code-review スキル |
| `skills/bugfix.yml` | 英語 | incident analysis スキル |
| `skills/change-request.yml` | 英語 | change analysis スキル |

スキル間で言語が統一されていない。discovery.yml は `output: 日本語` と明示。

### 1.3 GitHub Actions テンプレートの現状

`internal/actions/templates/` に 25 ワークフローテンプレート + 10 Wave テンプレートが存在。

- ワークフロー内のコメント・ラベル名: 英語
- Wave テンプレート内のプロンプト: 言語未指定（AI に委ねている）
- `teraflow-req-agent.yml`: Discussion コメントは日本語ロケール想定（`確定`、`要求確定` トリガー）

### 1.4 teraflow.yml の現状

`.github/teraflow.yml` には `language` フィールドが存在しない。
`confirmation.trigger: "確定"` と `confirmation.req_trigger: "要求確定"` が日本語でハードコード。


## 2. 対応範囲と優先順位

### 2.1 4 レイヤーの i18n 対象

| 優先度 | レイヤー | 対象 | 影響範囲 | 理由 |
|--------|---------|------|---------|------|
| **P1** | CLI メッセージ | エラー、ヘルプ、ステータス出力 | 全ユーザー | 最もユーザー接触頻度が高い |
| **P2** | AI プロンプト | スキル定義、Wave テンプレート | AI 応答品質 | 言語混在が応答品質を低下させる |
| **P3** | ワークフローテンプレート | GitHub Actions のコメント・ラベル | CI/CD 利用者 | セットアップ時のみ影響 |
| **P4** | ドキュメント生成 | CoDD 文書の言語 | 生成文書 | AI 生成言語に依存 |

### 2.2 teraflow.yml への language フィールド追加

```yaml
# .github/teraflow.yml
version: "1"

# 言語設定（新規追加）
language: "ja"  # ja | en（デフォルト: en）

project:
  name: "teraflow"

confirmation:
  trigger: "確定"        # language: ja のデフォルト
  req_trigger: "要求確定"  # language: ja のデフォルト
```

`language` フィールドは全レイヤーの言語決定のルートとなる。


## 3. 技術選定

### 3.1 Go i18n ライブラリ比較

| ライブラリ | Stars | 特徴 | 翻訳形式 | 複数形 | 推奨 |
|-----------|-------|------|---------|--------|------|
| **nicksnyder/go-i18n** | 3k+ | 業界標準、CLDR複数形対応 | JSON/TOML/YAML | ○ | **推奨** |
| **golang.org/x/text** | Go 公式 | message/language パッケージ | Go catalog | ○ | △ 学習コスト高 |
| **go-playground/universal-translator** | 1k+ | validator 連携向け | JSON | ○ | △ CLI 向きではない |
| **gotext** | 軽量 | gettext 互換 | PO/MO | ○ | △ Go エコシステムから外れる |

### 3.2 推奨: nicksnyder/go-i18n v2

**選定理由:**
1. Go i18n のデファクトスタンダード（最も利用実績が多い）
2. YAML 翻訳ファイル対応（teraflow の既存 YAML エコシステムと統一）
3. 複数形対応（CLDR ルール準拠）
4. `go generate` 連携でメッセージ ID の型安全性を確保可能
5. テンプレート統合（`{{.Count}}` 等の変数展開）

### 3.3 翻訳ファイル形式: YAML

**選定理由:**
- teraflow は YAML を全面的に使用（teraflow.yml, skills/*.yml, CoDD frontmatter）
- 開発者が追加の形式を覚える必要がない
- go-i18n v2 がネイティブ YAML 対応

**ディレクトリ構造:**

## 4. 言語検出

### 4.1 検出優先順位

```
1. teraflow.yml の language フィールド（最優先）
2. 環境変数 TERAFLOW_LANG
3. 環境変数 LANG / LC_ALL（OS ロケール）
4. フォールバック: "en"
```

### 4.2 実装設計

```go
// internal/i18n/i18n.go
package i18n

import (
    "embed"
    "os"
    "strings"
    "sync"

    "github.com/nicksnyder/go-i18n/v2/i18n"
    "golang.org/x/text/language"
    "gopkg.in/yaml.v3"
)

//go:embed locales/*.yaml
var localeFS embed.FS

var (
    bundle    *i18n.Bundle
    localizer *i18n.Localizer
    once      sync.Once
)

// Init initializes the i18n system with the given language.
// If lang is empty, detection priority is applied.
func Init(lang string) {
    once.Do(func() {
        bundle = i18n.NewBundle(language.English)
        bundle.RegisterUnmarshalFunc("yaml", yaml.Unmarshal)
        // embed されたロケールファイルを読み込み
        bundle.LoadMessageFileFS(localeFS, "locales/en.yaml")
        bundle.LoadMessageFileFS(localeFS, "locales/ja.yaml")

        resolved := detectLanguage(lang)
        localizer = i18n.NewLocalizer(bundle, resolved)
    })
}

// T translates a message by ID with optional template data.
func T(id string, data ...map[string]any) string {
    cfg := &i18n.LocalizeConfig{MessageID: id}
    if len(data) > 0 {
        cfg.TemplateData = data[0]
    }
    msg, err := localizer.Localize(cfg)
    if err != nil {
        return id // フォールバック: メッセージ ID をそのまま返す
    }
    return msg
}

func detectLanguage(configLang string) string {
    // 1. teraflow.yml の language
    if configLang != "" {
        return configLang
    }
    // 2. TERAFLOW_LANG
    if v := os.Getenv("TERAFLOW_LANG"); v != "" {
        return v
    }
    // 3. LANG / LC_ALL
    for _, key := range []string{"LC_ALL", "LANG"} {
        if v := os.Getenv(key); v != "" {
            // "ja_JP.UTF-8" → "ja"
            return strings.SplitN(strings.SplitN(v, ".", 2)[0], "_", 2)[0]
        }
    }
    // 4. フォールバック
    return "en"
}
```

### 4.3 CLI コマンドからの利用

```go
// cmd/root.go（初期化）
func init() {
    cobra.OnInitialize(func() {
        cfg, _ := config.Load(configPath)
        i18n.Init(cfg.Language)  // teraflow.yml の language フィールド
    })
}

// cmd/validate.go（使用例）
// Before:
fmt.Fprintf(cmd.OutOrStdout(), "Valid: %t\n", result.Valid)
// After:
fmt.Fprintln(cmd.OutOrStdout(), i18n.T("validate.valid", map[string]any{"Valid": result.Valid}))
```


## 5. AI 応答の言語制御

### 5.1 課題

現在の AI プロンプトは言語が混在している。discovery.yml は日本語、design.yml は英語。ユーザーの `language` 設定に関係なく固定言語で応答する。

### 5.2 方式: プロンプトへの言語指示注入

AI プロバイダーへのリクエスト時に、システムプロンプトの先頭に言語指示を自動注入する。

```go
// internal/agent/provider.go（拡張）
func (p *Provider) injectLanguageInstruction(systemPrompt, lang string) string {
    switch lang {
    case "ja":
        return "回答は日本語で行ってください。\n\n" + systemPrompt
    case "en":
        return "Please respond in English.\n\n" + systemPrompt
    default:
        return systemPrompt
    }
}
```

### 5.3 スキル定義の多言語化方針

#### 方式 A: 単一ファイル + 言語セクション

```yaml
# skills/discovery.yml
prompts:
  system:
    ja: |
      あなたは要件探索のスペシャリストです。...
    en: |
      You are a requirements discovery specialist. ...
```

#### 方式 B: 言語別ファイル

```
skills/
├── discovery.yml        # デフォルト（en）
├── discovery.ja.yml     # 日本語
└── discovery.zh.yml     # 中国語（将来）
```

**推奨: 方式 A**（単一ファイル + 言語セクション）

理由:
- ファイル数が増えない（管理コスト低）
- 言語間の差分が同一ファイル内で一目瞭然
- 新しい言語追加時にセクション追加のみ
- 既存のスキル読み込みロジックへの変更が最小

**未指定言語のフォールバック**: `en` セクションを使用。`en` も未定義の場合はルートの `system` を使用（後方互換）。

### 5.4 Wave テンプレートの言語制御

Wave テンプレート（`.tmpl`）には言語指示を含めず、Wave エンジンが実行時に言語プレフィクスを注入する。

```go
// internal/wave/engine.go
func (e *WaveEngine) buildPrompt(template string, lang string) string {
    langInstruction := languageInstruction(lang)
    return langInstruction + "\n\n" + template
}
```

これにより、テンプレートファイル自体は言語非依存を維持する。


## 6. GitHub Actions テンプレートの多言語対応

### 6.1 方針

GitHub Actions テンプレートは `setup templates` コマンドでリポジトリに展開される。展開時に `language` 設定に応じてテンプレート変数を解決する。

### 6.2 テンプレート変数方式

```yaml
# internal/actions/templates/teraflow-req-agent.yml
- name: Post response
  run: |
    HEADER="${{ env.TERAFLOW_LANG == 'ja' && '## 🔍 要件探索' || '## 🔍 Requirements Discovery' }}"
```

ただし、ワークフローテンプレートの多言語化は複雑度が高く、効果が限定的（セットアップ時のみ）。

**推奨**: Phase 3（最終段階）で対応。Phase 1-2 では英語のままとし、コメント本文の言語は AI 応答の言語制御（§5）で対応する。

### 6.3 ラベルの多言語対応

`confirmation.trigger` と `confirmation.req_trigger` は teraflow.yml で言語別デフォルトを設定する。

```yaml
# language: ja のデフォルト
confirmation:
  trigger: "確定"
  req_trigger: "要求確定"

# language: en のデフォルト
confirmation:
  trigger: "confirm"
  req_trigger: "requirements confirmed"
```

ユーザーが明示的に `confirmation` を設定している場合はそれを優先する。


## 7. CoDD ドキュメント生成の言語制御

### 7.1 方針

`doc generate` で生成される CoDD 文書の言語は、AI プロンプトの言語指示（§5.2）に連動する。追加の仕組みは不要。

### 7.2 frontmatter の言語フィールド

生成された CoDD 文書の frontmatter に `language` フィールドを追加する。

```yaml
---
codd:
  node_id: "req:feature-auth"
  title: "認証機能要件定義"
  language: "ja"    # 文書の記述言語
  status: "draft"
---
```

これにより、多言語プロジェクトでの文書管理が可能になる。


## 8. config パッケージの変更

### 8.1 Config 構造体の拡張

```go
// internal/config/config.go
type Config struct {
    Version      string            `yaml:"version"`
    Language     string            `yaml:"language"`     // 新規追加
    Project      ProjectConfig     `yaml:"project"`
    Confirmation ConfirmConfig     `yaml:"confirmation"`
    AI           AIConfig          `yaml:"ai"`
    // ...
}

// Language returns the configured language with fallback detection.
func (c *Config) Language() string {
    if c.Language != "" {
        return c.Language
    }
    return i18n.DetectLanguage("")
}
```

### 8.2 confirmation デフォルト値の言語連動

```go
func (c *Config) applyLanguageDefaults() {
    if c.Confirmation.Trigger == "" {
        switch c.Language {
        case "ja":
            c.Confirmation.Trigger = "確定"
            c.Confirmation.ReqTrigger = "要求確定"
        default:
            c.Confirmation.Trigger = "confirm"
            c.Confirmation.ReqTrigger = "requirements confirmed"
        }
    }
}
```

## 11. 新言語追加手順（将来拡張）

新しい言語を追加する手順:

1. `internal/i18n/locales/{lang}.yaml` を作成（en.yaml をコピーして翻訳）
2. `internal/i18n/i18n.go` の `Init()` に `bundle.LoadMessageFileFS` を追加
3. 各スキル YAML に `{lang}:` セクションを追加
4. テスト実行（翻訳カバレッジチェックで未翻訳キーを検出）

`embed.FS` を使用しているため、新ロケールファイルを配置するだけで自動的に組み込まれる。ユーザーが追加のインストールを行う必要はない。

| メッセージ抽出漏れ | 一部の出力が英語のまま残る | 翻訳カバレッジチェックで未翻訳を自動検出 |
| 翻訳品質のばらつき | ユーザー体験の低下 | Phase 1 は開発者自身が翻訳、将来は翻訳レビュープロセス導入 |
| AI 応答が言語指示を無視 | 英語で回答される場合がある | システムプロンプトの先頭に言語指示を配置（最も効果が高い位置） |
| go-i18n の依存追加 | バイナリサイズ微増 | embed.FS で翻訳ファイルをバイナリに含めるため、外部ファイル不要 |
| テンプレート変数展開のオーバーヘッド | CLI レスポンス遅延 | go-i18n のキャッシュ機構で実質無視可能 |
| 既存の日本語ハードコード（確定/要求確定） | 後方互換性 | language 未設定時は現行動作を維持（フォールバック） |
